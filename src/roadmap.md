#### 新增检测场景

r[roadmap.memory-mangement.kmiri]

* [x] 页表/映射一致性：页表状态跟踪和使用合法检测
* [ ] 共享内存映射：
    * 并发一致性问题：多进程/多线程同时读写，缺少锁或原子操作，出现数据竞争、撕裂写、可见性问题（缓存/内存序）
    * 生命周期问题：一方 munmap/关闭/重建后，另一方仍在访问，导致悬空映射、UAF 风险或崩溃
    * 页一致性与失效问题：页表更新、回收、迁移、mprotect 后若同步/失效处理不当，可能出现旧映射被继续使用（TLB 相关一致性风险）
* [ ] 外设内存管理：DMA/IOMMU/MMIO
    * 映射正确性：map/unmap 不配对、重复 unmap、方向错误
    * MMIO 访问合法性：宽度/对齐/字节序错误、访问未映射区域
* [ ] 多地址空间管理
    * 页表修改后漏做 TLB 失效：导致旧映射继续生效、越权/UAF
    * VMA 合并/拆分边界错误：mmap/munmap/mprotect 后崩溃或权限错
    * IOMMU 映射与 CPU 页表语义不一致：DMA 越界、设备写坏内存
* [ ] 多核页表并发问题
    * TLB 一致性：stale TLB、漏 shootdown、过早回收旧页，页表页、映射页的 refcount 与释放时机是否和 TLB 失效同步
    * 内存序/屏障：PTE 写入、发送 IPI、远端 ack、释放页的先后是否有屏障保证，没有屏障会极低概率随机崩溃、偶发越权访问
    * 锁与竞态：对于页表锁、VMA 锁、rmap 锁在多核下的顺序与上下文合法性，检测死锁、锁反转、数据竞争
    * 缺页并发：跟踪并发 fault、COW、mprotect/munmap 与 fault 并行时的状态机，从而避免错误映射、权限错、崩溃

### 中断机制

r[roadmap.interrupt]

处理关键：异步事件通知（内核发起、硬件发起、异常陷入）、调度与时间、IPI

1. 主动发起：

|          | 本核 CPU 接收                                                    | 其他核 CPU 接收                                     |
|----------|------------------------------------------------------------------|-----------------------------------------------------|
| 硬件发起 | 设备中断（GPIO/NIC/磁盘）、定时器中断、本地 APIC timer           | 由中断控制器路由到指定核（如 MSI/MSI-X 配置到某核） |
| 内核发起 | 本地软中断触发、deferred work 唤醒本核处理、`raise_softirq` 路径 | **IPI**（reschedule、TLB shootdown、call function） |

2. **同步异常/陷阱（CPU 执行触发）**：如 page fault、除零、syscall trap。它不是“外部发起中断”，而是当前指令流导致，通常由“当前核自己接收并处理”。

### 任务管理

r[roadmap.task]

原 Miri 的任务管理单实例内多线程调度、多实例模拟多进程执行。

KMiri 的任务调度方式：在一个实例中同时调度多核、多线程、多进程。如果纯软件模拟，这没有达到多核并行的效果，执行效率也会很差，因此需要考虑如何以并行方式解释 MIR？

暂时没考虑多核并发问题检测清单。以具体代码为导向，在适配内核过程中，再考虑如何支持多核。

### 用户态检测

r[roadmap.syscall-trace-replay]
