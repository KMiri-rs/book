## 0. 结论（组会直接讲这一页）

1. **定位：** KernMiri（星绽 ATC'25 §6.3）解决了**内存环境**的问题：物理页、页状态、页表翻译。本文解决**执行环境**：中断、中断上下文、抢占这些**异步控制流**。这是前作完全没碰过的部分，也是新论文的贡献所在。
2. **关注的 UB 有四类（U1–U4，见第 2 节）：**
   - **U1** 中断重入造成的别名冲突和 UAF。
   - **U2** 原子模式和中断上下文契约被违反。
   - **U3** 异步回调的生命周期错误。
   - **U4** 抢占造成的任务间数据竞争。

   代码局部的容器类 UB、KMiri 自身的建模缺陷、设备和 DMA、用户程序本身的 bug，都**不在**论文的主张范围内。
3. **中断支持范围：**
   - **必做：** 本地中断开关状态、**定时器中断**、完整的上半部和下半部处理路径、中断返回时的抢占。
   - **第二步：** 嵌套中断（OSTD 原生支持两级），以及“触发任意已注册中断线”（不带设备模型）。
   - **与双核绑定再做：** IPI。
   - **首篇不做：** 用户态发起的特权切换（syscall、用户缺页）。理由见第 3 节。
4. **评测：**
   - 主实验是**消融**：同一批测试分别在 KMiri 事件关（约等于 KernMiri）和 KMiri 事件开下运行。
   - 配两个“现状” baseline：普通 Miri 跑单元测试，以及 QEMU 原生多次运行。
   - bug 来源有三个：历史 bug、**守卫降级变异**（系统地注入缺陷）、新发现。
   - KASAN 只做能力对比。星绽没有 KASAN（快照里搜不到任何 kasan、sanitizer 代码），不作为主 baseline。
   - **“第一个把 Rust UB 检查带进内核”这句话不能说**，KernMiri 已经做过。
5. **双核：** 首篇**不强制**。单核的中断加抢占是必需的；所有状态从第一天起就按 CPU 维度设计，双核（IPI、迁移、TLB shootdown）作为有截止日期的加分项。
6. **BlueOS：** 只做**任务切换和中断**，不做分页。它选用的 `qemu_riscv64` 配置本身就是 `page_table=false`，而且它是抢占式内核，U1–U4 都适用。前提是先把它目前会 panic 的任务切换做通。

## 1. 定位：前作管内存环境，本文管执行环境

星绽把 UB 分成三层（KMiri Book 引言也采用了这个划分）：

- **语言级：** Miri 本来就能查。
- **环境级：** 页状态、映射，以及栈和上下文。
- **架构级：** 中断控制器、IOMMU 这类硬件契约。

KernMiri 把**内存**这一半的环境级 UB 接进了 Miri，**执行上下文**这一半至今是空白。

**证据【源码确认】**，星绽 `ostd/src/arch/miri/irq.rs`：

```rust
pub(crate) fn enable_local() {}
pub(crate) fn disable_local() {}
pub(crate) fn is_local_enabled() -> bool { true }
pub(crate) fn enable_local_and_halt() {}
pub(crate) fn send_ipi(cpu_id: HwCpuId, guard: &dyn PinCurrentCpu) {}
```

由此带来两个后果：

**后果一：中断处理代码完全不可达。** 定时器回调、`IrqLine` 回调、下半部处理在 KMiri 里从来不会在“打断别的代码”的时刻执行。

**后果二：星绽自己写的安全检查在 KMiri 里形同虚设。** `ostd/src/task/atomic_mode.rs`：

```rust
pub fn might_sleep() {
    let preempt_count = super::preempt::cpu_local::get_guard_count();
    let is_local_irq_enabled = crate::arch::irq::is_local_enabled();   // KMiri 里恒为 true
    if (preempt_count != 0 || !is_local_irq_enabled) && ... {
        panic!("This function might break atomic mode ...");
    }
}
```

同一文件的注释写道：*"Key kernel primitives such as `SpinLock` and `Rcu` rely on the atomic mode for correctness or **soundness**."* 也就是说，**关中断状态是星绽 safe API 健全性的前提**，而 KMiri 现在根本不维护这个状态。

**论文一句话：** 让 Rust 内核在**异步控制流**下的 UB 可达、可检。中断可以在合法时刻到达，执行真实的处理代码；中断上下文和原子模式状态由解释器如实维护；Miri 原有的检查（借用、UAF、数据竞争、死锁）在这些路径上全部有效。

## 2. 我们关注的 UB（结论）

### 2.1 关注清单

| 编号 | 类别 | 典型形态 | 报出方式 | 单核能否触发 |
|---|---|---|---|---|
| **U1** | **中断重入导致的别名冲突和 UAF** | 任务只关了抢占、没关中断，就持有 `&mut` 访问共享数据；中断处理器访问同一数据 | Miri 原有的 SB/TB 和 UAF 检查 | 能 |
| **U2** | **原子模式和中断上下文契约违反** | 关中断或持自旋锁时睡眠；中断处理器拿了“任务侧不关中断”的锁（例如 `WriteIrqDisabled` 的写锁、`PreemptDisabled` 自旋锁）；不在关中断状态下访问 CPU-local | 星绽自带的 `might_sleep` 检查**开始生效**；KMiri 新增中断上下文死锁诊断 | 能 |
| **U3** | **异步回调生命周期错误** | 定时器或下半部回调访问已释放的对象；取消与触发竞争 | UAF 检查 | 能 |
| **U4** | **抢占造成的任务间数据竞争** | 两个任务没加锁就访问共享数据，靠“不会被抢占”的错误假设；中断返回时被抢占 | Miri 向量时钟。**前提：抢占式切换不能凭空制造 happens-before** | 能（单核抢占）；跨核迁移版本需要双核 |

**为什么是这四类：**

- 它们都只在“异步事件打断正在执行的代码”时出现：前作不覆盖，普通 Miri 也不可达。
- 它们最终都由 **Miri 已有的检查**或**星绽自带的检查**报出，我们不用发明新的“bug 定义”，审稿人容易接受。
- 它们都能在**单核**上触发，所以不依赖双核。

### 2.2 不关注（不进入论文的检测主张）

| 不关注 | 原因 |
|---|---|
| 代码局部的容器类 UB（例如 BlueOS 那 10 个 rbtree、ilist issue） | 普通 Miri 跑单元测试就能查到。KMiri 运行中顺带发现的可以报告，但单独计数，不算方法贡献 |
| KMiri 自身的建模缺陷（v1 的 M1：对象复活漏报、分配器回收误报、复制初始化） | 是我们自己工具的 bug，作为**前置工程**修掉（第 8 节） |
| 设备、DMA、IOMMU 行为 | 需要设备模型，不在 Rust UB 主线上 |
| 用户程序本身的 bug、任意 ELF 执行 | KMiri 解释的是 Rust MIR，不是机器码 |
| 纯逻辑错误（不构成 UB、也不违反契约） | 没有可靠的检查依据 |

### 2.3 每类一个代表案例（缺陷写法都按星绽真实 API 写成，属于【设计/注入】）

**U1：中断重入导致的别名冲突**

```rust
fn record(e: Event) {
    let _g = disable_preempt();                       // 缺陷：应该关中断
    let s: &mut Stats = unsafe { &mut *STATS.get() };
    s.events.push(e);                                 // ← 定时器中断到达
}
fn on_timer(_: &TrapFrame) {
    let s = unsafe { &mut *STATS.get() };
    s.events.clear();
}
```

中断返回后 `record` 继续使用 `s`，SB/TB 报借用已失效；如果 `clear` 释放了缓冲，就报 UAF。

**U2：契约违反，单核死锁**

`ostd/src/sync/guard.rs` 中 `WriteIrqDisabled` 的文档写明 *"The user must ensure that the IRQ handlers never take the write lock"*【源码确认】。缺陷写法是在中断处理器里拿写锁：任务持读锁时（中断开着）来了中断，处理器自旋等写锁，而读锁的持有者要等处理器返回才能继续，于是永远等下去。

U2 的另一半更简单：只要 KMiri 如实维护关中断状态，**星绽自己的 `might_sleep` 就能报出“关中断时睡眠”**，不需要我们写任何新的检查。

**U3：定时器回调 UAF**

```rust
let buf = Box::new([0u8; 64]);
let p = &*buf as *const _ as usize;
timer.set_timeout(ms(10), move || unsafe { log((p as *const [u8; 64]).read()) });
drop(buf);                                            // 缺陷：没先取消定时器
```

**U4：抢占式数据竞争**

两个任务对同一个 `static` 计数器做非原子的 `+= 1`，作者以为“同一 CPU 上不会被打断”。真实单核机器上，定时器抢占会让两次读改写交错。KMiri 在中断返回处触发真实调度器的抢占；只要抢占切换本身不产生同步关系，向量时钟就会报数据竞争。

## 3. 中断支持到什么程度（结论）

### 3.1 星绽里的“中断类”事件全景

| 种类 | 谁发起 | 同步还是异步 | 星绽中的位置 | 结论 |
|---|---|---|---|---|
| **定时器中断** | 硬件（本地定时器） | 异步 | `timer::register_callback_on_cpu`、`call_timer_callback_functions` | **必做（v1）** |
| 中断返回时的抢占 | 内核（中断尾部） | 异步的结果 | 调度器的抢占检查 | **必做（v1）** |
| 下半部（L1 bottom half） | 内核（上半部结束后） | 异步的结果 | `irq::register_bottom_half_handler_l1` | **必做（v1）**：它是中断路径的一部分，回调可以重新开中断 |
| 设备中断（`IrqLine` 回调） | 硬件（外设） | 异步 | `IrqLine::on_active` | **第二步（v2）**：不做设备模型，只提供“触发某条已注册中断线”。代码可达，设备状态由测试准备 |
| 嵌套中断（L2） | 硬件 | 异步 | `InterruptLevel`，`register_bottom_half_handler_l2` | **第二步（v2）**：OSTD 明确支持两级嵌套，L1 下半部开中断后就可能嵌套 |
| IPI | 内核（另一个 CPU） | 异步 | `send_ipi`、`inter_processor_call`、TLB shootdown | **与双核一起做（v3）**：单核上没有意义 |
| 系统调用 | 用户（特权切换） | **同步** | `UserContext::execute` 返回 `ReturnReason::UserSyscall` | **首篇不做** |
| 用户态异常、缺页 | 用户 | **同步** | `ReturnReason::UserException` | **首篇不做** |
| 内核态缺页（访问用户内存时） | 内核 | 同步 | 可失败的用户内存复制（`kern_miri_copy` 尚未实现） | 前置工程。作为“复制返回错误”的语义处理，不建模成真实的中断 |
| NMI、机器检查、除零等 CPU 异常 | 硬件 | 同步或异步 | — | 不做：Rust 里多数已经是 panic，或者与 Rust UB 无关 |

### 3.2 为什么首篇不做用户态发起的切换

1. **它不产生新的交错。** 系统调用和用户缺页发生在**确定的位置**（用户执行 `syscall` 指令时），进入内核后是一段顺序执行。它扩大的是**代码覆盖面**，不是**事件语义**，不属于本文“异步控制流”的主张。
2. **它覆盖的 bug 类型不同。** 系统调用路径上的典型问题是用户指针校验和参数处理，更接近“输入驱动”的 bug，适合用模糊测试类工具，而不是本文的方向。
3. **成本高。** 要么执行用户机器码（KMiri 做不到），要么写“脚本化用户返回”。
4. **可以留作扩展：** 星绽 Miri 版 `UserContext::execute` 已经是“`run()` 之后按 trap 号分派”的结构【源码确认】，以后让 `run()` 按脚本返回一个合成的 syscall 号和寄存器即可。这样无需特权切换，就能把内核 syscall 处理代码放进检查。可以写进 Future Work，或者作为第二篇。

### 3.3 版本规划

| 版本 | 内容 | 能覆盖的 UB |
|---|---|---|
| **v1（首篇必需）** | 单核；解释器维护每个 CPU 的中断开关状态和中断层级；虚拟时间驱动的定时器源；只在中断打开时、在 MIR 语句边界上注入（用种子控制，有次数上限，可记录和重放）；在被打断的线程上嵌套执行**真实的**上半部和 L1 下半部；中断返回时做抢占检查；抢占切换不产生 happens-before | U1、U2、U3、U4 的单核版本 |
| **v2** | 嵌套中断（L2）；触发任意已注册中断线；注入策略从随机升级为对指定区间有界枚举 | 下半部和嵌套边界上的 U1、U2；驱动上半部的可达性 |
| **v3（加分）** | 双核：真实 AP 启动、per-CPU 重定位、迁移、IPI、跨核 TLB shootdown | U4 的跨核版本，以及 TLB 契约 |

## 4. 机制设计要点（v1）【设计】

1. **中断状态归解释器管理。** 新增 shim（暂定 `kern_miri_irq_enable`、`kern_miri_irq_disable`、`kern_miri_irq_is_enabled`、`kern_miri_halt`），每个 CPU 一个中断开关标志。星绽 `arch/miri/irq.rs` 改为调用这些 shim。完成后 `might_sleep` 等现有检查**自动生效**。
2. **定时器源。** 虚拟时间按执行步数推进，到期时把定时器中断置为待处理；`halt` 时直接跳到下一个到期时刻，否则 idle 只会空转。
3. **注入点。** 待处理且中断已开时，可以在 MIR 语句边界注入。“是否注入、在哪注入”由种子决定，总次数有上限；每次运行记录事件轨迹，以便重放。
4. **处理器执行。** 在当前线程压入一个“中断帧”，调用星绽真实的中断分派代码（上半部回调 → L1 下半部 → 返回时的抢占检查），然后恢复被打断的代码。处理代码全部被解释、全部接受检查。
5. **并发语义。** 同一 CPU 上，中断处理器和被打断的代码是**程序顺序**，不报数据竞争，但**借用冲突照常检查**（U1 靠的就是这个）。抢占式任务切换**不加** happens-before，主动切换的同步关系来自调度器真实的锁和原子操作（U4 靠的就是这个）。
6. **中断上下文死锁诊断。** 中断处理器自旋等待的锁，如果由被它打断的同 CPU 执行流持有，就报死锁并附上两边的调用栈。

**v1 验收标准：**

- 第 2.3 节四类缺陷写法都报出预期的错误；对应的正确写法全部通过。
- 星绽现有 7 个集成测试，以及 OSTD 中能在 KMiri 下运行的 ktest，在事件开启后不出现新增误报。
- 同一种子重放结果一致。

## 5. 评测与 baseline（结论）

### 5.1 先回答三个疑问

**疑问一：“我们是第一个，没有可比的对象”能不能说？**

**不能。** 把 Rust UB 检查带进内核这件事，KernMiri 已经做过（前作）。如果只说“第一个”，审稿人一定会问“比 KernMiri 多了什么”。本文必须拿**同一批测试**展示前作抓不到、本文抓得到。好在这个对比正好可以通过**消融**做出来（见 5.2）。

**疑问二：对 B 类 bug，Miri 是不是整列都是空的，表格还有没有意义？**

你的理解基本对：**普通 Miri 跑不了内核**，把“在整个内核上跑 Miri”当一列，结果全是“无法运行”，没有信息量，不要这样列。

有意义的比较对象是**开发者今天实际怎么用 Miri**：在宿主机上用 `cargo miri test` 跑可单独编译的 crate 单元测试。这一列的价值不在于“抓到 0 个”，而在于**说明原因**。我们把它分成三种结果：

- **无法运行：** 被测代码依赖内核环境。
- **能运行但不可达：** 单元测试里不会来中断，缺陷路径永远走不到。
- **需要已知 bug 才能构造：** 只有事先知道 bug，手写“在第 N 行调用处理函数”，Miri 才报得出来。

第三种情况恰好说明：**Miri 的检查本身没问题，缺的是让事件发生的机制**。这正是本文的论点。另外，开发者如果用 `std::thread` 模拟中断，关中断就毫无意义，会产生大量误报，语义也不对（中断处理器应该跑完才返回，线程却会交错）。可以挑 1–2 个例子演示，作为“为什么不能用普通 Miri 加测试桩”的论据。

**疑问三：要不要和 KASAN 这类 sanitizer 比？**

**做能力对比，不做主实验。** 理由有三：

1. **星绽没有 KASAN**：源码快照里没有任何 kasan、sanitizer 代码【源码确认】。要比就得先给星绽实现 KASAN 运行时，这不是我们的贡献，工作量也大。
2. **两者是互补关系，不是替代关系。**
   - KASAN 检测的是“地址级”的越界和 UAF，而且**要等 bug 在真实时序里碰巧发生**。
   - KMiri 能检测 Rust 特有的别名违规（SB/TB）、非法值、provenance，能**控制中断时机**，代价是慢几个数量级。
   - U1 的别名冲突在没有造成实际内存损坏前，KASAN 看不到；U3 的 UAF 只要碰巧触发，KASAN 能看到，但触发靠运气。
3. **如果审稿人要求定量对比：** Linux/RFL 那条线有 KASAN（对 Rust 代码的支持程度要在我们的环境里确认），可以拿已有的 RFL 案例（#1261、#1265、drm 重复 drop）在 KASAN 下各跑一遍，作为小实验放进讨论。KCSAN（数据竞争）和 KMSAN（未初始化）同理，只做能力对比。

### 5.2 推荐的评测设计

| 配置 | 含义 | 作用 |
|---|---|---|
| **A. 普通 Miri** | 宿主机单元测试 | 现状一：开发者用 Miri 能做到什么 |
| **B. QEMU 原生运行** | 同一测试原生运行 N 次，可以加压力测试 | 现状二：内核测试能否暴露问题。通常要么静默损坏，要么偶发卡死 |
| **C. KMiri 事件关** | 中断、抢占模型关闭，约等于 KernMiri | **前作**，也就是消融基线 |
| **D. KMiri 完整** | 本文 | — |

主结果是 **C 对 D 的消融**：同一测试、同一检查模式、同一预算，比较检出的差异。D 比 C 多检出的部分，就是本文的贡献。A 和 B 用来说明“现有手段为什么不够”。

### 5.3 bug 从哪来（解决“真实 bug 太少”的风险）

1. **历史 bug：** 在星绽提交历史里找修复中断、定时器、抢占、原子模式、per-CPU、唤醒相关问题的提交，回退到修复前，看各配置能否检出。
2. **守卫降级变异（推荐作为主要定量来源）：** 在**真实内核代码**里系统地把安全写法降级。例如：
   - 把 `LocalIrqDisabled` 换成 `PreemptDisabled`。
   - 把 `disable_local()` 换成 `disable_preempt()`。
   - 把 `issue_tlb_flush_with` 换成 `issue_tlb_flush` 并立即释放页。
   - 删掉定时器取消。

   每个变异都是一个“候选缺陷”，统计 A、B、C、D 四种配置的检出率；**原版代码**用来测误报。好处有三：数量可控、有客观分母、贴近真实写法，不是凭空编的玩具例子。注意：并非每个变异都真的构成 bug（例如某把锁实际上从不在中断里使用），需要人工判定后分类。
3. **新发现：** 在星绽的定时器、中断、同步原语路径上直接运行完整 KMiri。

三类来源分开计数，不混在一起。

## 6. 两个待定问题的结论

### 6.1 首篇是否必须包含双核？**不强制，但按双核来设计。**

- U1–U4 都能在单核上触发，本文的核心主张（异步控制流）不依赖双核。
- 双核会一次引入 AP 启动、per-CPU 重定位、IPI、迁移、跨核 TLB 等多个未知因素。在单核中断模型验证之前上双核，出了问题很难归因。
- **但** 中断开关、中断层级、待处理队列从第一天起就按 CPU 维度设计。到预定节点（建议在 v1 验收之后定一个日期）如果进度允许，就做 v3，补上跨核迁移版的 U4 和 TLB shootdown，作为加分。审稿人问“内核都是多核的”，可以用 v3 的结果回答，或者在限制一节说明。

### 6.2 BlueOS 只做中断、不做分页？**是。**

- BlueOS 目前的 KMiri 配置（`qemu_riscv64`）就是 `page_table=false`【已实测，boot-status 报告】，做分页没有对象。
- BlueOS 是抢占式内核，有定时器、线程超时和唤醒，U1–U4 都适用，正好用来证明**中断模型能迁移到第二个内核**。
- **前提：** BlueOS 当前路径不加载应用，普通任务切换会 panic，boot 只有 10 轮 idle【已实测】。所以先打通任务切换，再接中断。要在论文里报告接入的改动量（Mirch 层行数、新增 shim 数）。
- Tock 不适合作为第二个目标：它的硬中断在处理函数里只记录事件，回调延后到主循环执行，内核内部几乎不存在“中断打断持锁代码”的情形，与 U1、U2 不对口。

| 问题 | 证据 | 为什么挡路 |
